# BizOS 法定主体与经营单元树解耦设计

日期：2026-09-22

## 目标

BizOS 将法定主体与经营组织拆成两个相互独立的业务维度：

- 法定主体表示签约、责任、开票、结算和账簿边界。
- 经营单元表示内部经营管理归属，可以组成任意深度的树。
- 一笔业务分别指定一个法定主体和一个经营单元。系统不维护、也不校验二者之间的绑定关系。
- 经营报表既可按法定主体统计，也可按任意经营单元节点汇总其全部后代。

这次改造覆盖核心主数据、权限范围、销售与采购业务、CRM、经营分析和 Agent 查询/写入。现有业务事实保留原来的法定主体和叶子经营单元，不重写历史单据。

## 已确认的业务规则

1. 法定主体与经营单元是并列维度，不建立一对一、一对多或多对多关系表。
2. 经营组织是一棵单根树。根节点表示最高经营主体，下级可以持续拆分为事业部、业务线、区域、团队等经营单元，不限定层数。
3. 业务创建时分别选择法定主体和经营单元。两者都必须启用且调用者分别具备权限，但无需形成预设组合。
4. 经营单元的父节点只能是另一个经营单元；禁止自引用和循环。
5. 停用或移动经营单元不改写历史单据上的经营单元 ID。
6. 第一阶段历史报表按“当前组织树”汇总，单据的原始叶子归属保持不变。若将来需要查看“当时的组织结构”，另行增加有效期版本，不在本期引入。

## 方案选择

考虑过三种实现：

1. 继续让经营单元带可空的 `legal_entity_id`。迁移小，但数据模型仍暗示两者存在关系，后续代码容易重新引入配对校验，不采用。
2. 经营单元使用 `parent_id` 邻接表，查询时用递归 CTE 展开后代。结构清楚、不依赖 PostgreSQL 扩展，适合目前组织规模，采用。
3. 邻接表加闭包表或 `ltree`。大树汇总性能更稳定，但写入、移动和一致性维护显著复杂，现阶段没有必要。

采用方案 2。为高频报表预留后续增加闭包表或物化路径的空间，API 和业务模型不暴露具体树存储方式。

## 数据模型

### 经营单元

`business_units` 调整为：

```text
id                       UUID PK
parent_business_unit_id  UUID NULL FK -> business_units(id) ON DELETE RESTRICT
code                     TEXT UNIQUE
name                     TEXT
status                   active | disabled
version                  BIGINT
created_at / updated_at
```

删除 `business_units.legal_entity_id`。增加防止直接自引用的检查约束；跨多级循环由服务层在同一事务中用递归查询拒绝。

数据库只允许一个启用的根经营单元。第一阶段不增加“层级类型”枚举，名称和编码表达事业部、区域、团队等含义，避免把组织形态写死。

### 业务事实

销售订单、采购订单、经营调整、CRM 商机等已经同时持有 `legal_entity_id` 和 `business_unit_id` 的记录继续保留两个字段。创建和更新时分别验证：

- `legal_entity_id` 指向启用的法定主体；
- `business_unit_id` 指向启用的经营单元；
- 当前主体对两个维度分别有数据权限。

删除“经营单元必须属于所选法定主体”的验证。

下游事实从来源单据继承两个维度。需要补齐 `business_unit_id` 的结算、收发货或利润事实，在本次迁移中按其来源单据回填；不存在可靠来源的表不猜测归属，保持当前维度并列能力或列入后续迁移清单。

### 客户、供应商与仓库

本期不把客户、供应商和仓库重构成全集团共享主数据，以控制风险；它们现有的 `legal_entity_id` 与 `business_unit_id` 字段视为两个独立的默认/管理归属，而不是合法组合。创建业务时：

- 客户或供应商仍需满足调用者对象权限和启用状态；
- 不再要求客户/供应商的经营单元等于单据经营单元；
- 涉及法定所有权的仓库仍需与业务法定主体一致，经营单元仅作管理归属，不参与法定主体配对校验。

后续若要让同一客户或供应商跨全部主体复用，应作为单独的集团往来方主数据项目处理。

## 组织树操作

核心主数据 API 为经营单元增加：

- `parentBusinessUnitId`：根节点为空；
- `ancestorPath`：只读，从根到父节点；
- `depth`：只读；
- `descendantCount`：只读，用于界面与停用影响提示。

新增、重命名、移动、停用继续使用现有主数据变更和审计机制。移动节点时在一个事务内锁定目标节点和新父节点，拒绝以下情况：

- 新父节点不存在或已停用；
- 节点成为自己的父节点；
- 新父节点位于该节点的后代中；
- 操作者对节点原子树或目标父子树缺少管理权限。

停用父节点前必须先停用全部启用的后代，或由用户明确执行“停用整个子树”的单独操作。默认不级联，避免意外冻结大范围业务。

## 权限模型

法定主体权限与经营单元权限继续分别存在：

- `legal_entity_ids` 精确表示可访问的法定主体集合；
- `business_unit_ids` 表示授权根节点集合，运行时展开为这些节点及全部后代。

鉴权快照新增“有效经营单元集合”，由授权根节点通过递归 CTE 计算。所有查询和命令仍同时应用两个维度的交集：用户必须能访问单据的法定主体，也必须能访问单据的经营单元。这里的交集只用于授权，不表示两个主数据对象建立了绑定关系。

移动经营单元会改变其当前子树的有效权限范围，因此必须写入审计事件，并撤销受影响的 Agent 委托/缓存快照，下一次请求重新计算。

## 查询与经营报表

所有按经营单元筛选的查询支持：

- 精确节点：仅该经营单元；
- 子树：该经营单元及全部后代，作为界面和报表默认；
- 多节点：多个授权节点子树的去重并集。

法定主体筛选独立应用。用户可以只选法定主体、只选经营单元、或同时选择二者。货币汇总继续遵守现有单币种约束，不跨币种直接求和。

报表结果返回所用的经营树节点和筛选模式，避免用户误以为看到的只是当前节点。

组织调整后，历史单据仍保留原叶子经营单元，但按当前树重新归入新的上级。这一行为会在界面提示中明确说明。

## API、Agent 与兼容性

现有业务创建输入仍保留 `legalEntityId` 和 `businessUnitId`，因此客户端与 Agent 不需要改变字段名称。语义调整为分别校验，不再查找二者的关联。

核心主数据的经营单元输入删除 `legalEntityId`，增加可空的 `parentBusinessUnitId`。读接口在兼容窗口内仍返回 `legalEntityId: null`，前端和 Agent 完成升级后再移除该兼容字段。

Agent 名称查找分别返回法定主体和经营单元候选。创建业务时若任一维度缺失或名称匹配不唯一，必须分别追问；不得根据另一维度推断或自动填入。

## 界面设计

核心数据中心的线性“法定主体 → 经营主体 → 业务对象”改成两个并列区域：

- 法定主体：保持列表维护。
- 经营组织：树形页面，支持展开/折叠、选择节点、新增下级、重命名、移动和停用影响查看。

销售、采购、CRM 等表单将“法定主体”和“经营单元”作为两个独立必填选择器。选择其中一个不会过滤另一个。经营单元选择器显示完整路径，例如“集团经营体 / 华东事业部 / 杭州团队”。

列表和详情同时显示两个字段；报表筛选器允许独立组合。

## 迁移方案

迁移必须可回滚到部署前备份，不在原迁移文件上修改历史：

1. 新增 `parent_business_unit_id`，暂时保留旧 `legal_entity_id`。
2. 创建一个根经营主体，将所有现有经营单元挂到根下；现有 ID、编码和业务引用不变。
3. 更新视图、API 和业务校验，使代码不再读取 `business_units.legal_entity_id`。
4. 更新权限展开、报表和界面，并运行兼容期验收。
5. 通过数据库查询确认没有运行路径或视图依赖旧列后，再在后续迁移中删除 `legal_entity_id`。

如果当前只有一个默认经营单元，它作为根节点使用，不额外创建重复根节点。若存在多个顶级经营单元，则创建一个中性的集团经营根节点承接它们。

迁移不修改销售、采购、CRM 和历史事实记录中的 `legal_entity_id` 或 `business_unit_id`。

## 失败处理与审计

树结构冲突、循环、停用依赖和乐观锁冲突使用明确的业务错误码。所有经营单元新增、移动、停用都记录旧父节点、新父节点、操作者、版本和 Trace ID。

部署采用扩展—迁移—收缩顺序。任一阶段失败时，旧列仍保留，服务可回滚到上一镜像；确认稳定前不执行收缩迁移。

## 验收标准

自动化验证至少包括：

- 可创建三层以上经营树并移动叶子节点；循环和自引用被拒绝；
- 一个经营单元可分别用于两个不同法定主体的业务单据；
- 选择法定主体不会过滤经营单元候选，反之亦然；
- 节点权限可以访问其全部后代，不能访问兄弟树；
- 销售、采购、CRM 创建和读取分别执行两个维度的权限校验；
- 上级经营单元报表等于其后代事实的去重汇总；
- 移动节点不改变历史单据的叶子经营单元 ID；
- 现有业务数据迁移后数量、金额、状态和审计链保持一致；
- Agent 按名称分别解析两类主体，不再推断配对关系；
- 真实 Business Dock 中可维护树、创建跨原法定主体边界的测试草稿并查看汇总。

## 非目标

本期不引入法定主体与经营单元映射表，不实现有效期组织版本，不重构客户/供应商为集团级统一主数据，不跨币种合并经营指标，也不改变法定账簿、仓库所有权和结算规则。
