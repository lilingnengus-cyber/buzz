# 退货助手接入：事务基础与剩余工作

## 已验证的 Core 修复

1. 采购退货发运和供应商签收改用供应商范围，避免把 supplier_id 当 customer_id 检查。撤销供应商范围后，新操作和原幂等请求均不可访问。
2. 销售/采购退货草稿对来源单据取得排他锁后再计算剩余可退量。隔离 PostgreSQL 的插入门闩测试让两个请求进入可观察的锁等待；旧实现两张草稿都占用最后一件，修复后仅一张成功，另一张因剩余不足被拒绝。
3. 两类退货确认同时更新持久化版本和更新时间，修复返回 v2、实际仍 v1 的错误。取消、质检和物流状态更新也刷新 updated_at。
4. 创建、确认、取消、质检读取/写入、采购发运/签收补齐来源订单业务单元、订单品牌、来源行冻结品牌与当前商品品牌范围。原有法人、仓库、客户/供应商和操作权限检查继续执行。

## 验证

隔离 B2 全闭环通过，包含现有订单、履约、结算、取消、库存逆转以及新增两类并发退货测试。新采购链为采购订单→收货→退货创建/确认→发运→供应商签收，核对 v1/v2/v3/v4、幂等、撤权、过期版本、库存仍为 1 件和应付仍为 100。新销售链为期初→销售→出库→退货确认→半数接受/半数报废，核对 v1/v2/v3、库存 0.5 件、隔离 0、库存价值 25、应收 100。撤销业务单元或品牌范围的写入与质检读取拒绝通过。

负向证据：旧供应商检查使合法发运返回 NotFoundOrForbidden；旧共享锁使两张并发草稿同时成功；修复权限后测试进一步发现并证明持久化版本缺陷。最终数据库 `return_scopes_final2` 全闭环通过。Core 严格 Clippy、格式和文件大小检查结果见本轮日志。

本批尚未部署，不代表助手已支持退货。线上仍为 83 工具配套版本。

## Core 来源读取与草稿入口

新增服务鉴权入口 `GET /v1/agent-return-sources/{sales_return|purchase_return}/{id}` 与 `POST /v1/agent-drafts/returns/{sales_return|purchase_return}`。来源返回当前版本、逐行来源数量、已被草稿/确认退货占用数量、剩余可退量、原始金额/成本、SKU 与范围字段。金额和数量使用十进制字符串；采购来源成本只代表原收货成本，不能当成最终退货确认成本（后者仍依赖执行时移动平均成本）。

草稿入口要求正数 expectedSourceVersion，Core 在来源排他锁取得后比较，随后重新计算可退量。原浏览器输入仍可省略该字段，省略时序列化不会新增字段，保留既有幂等摘要兼容性。创建仅保存 draft，不改变库存或往来，不表示退货确认成功。

新隔离数据库 `agent_return_drafts` 完整 B2 闭环通过：销售/采购来源逐行读取、当前版本、缺版本拒绝、旧版本冲突、未知字段拒绝、品牌/业务单元/仓库撤权后读写拒绝、草稿创建、幂等重放、同键变更原因冲突、创建后可退量减少。此前并发退货及完整销售质检/采购发运签收链继续通过。Core 严格 Clippy、格式与文件大小门禁通过。

这是 Core 入口验证，尚未接入 Gateway/Read API/MCP/Host，尚未部署或进行真实聊天验收。退货修改、确认影响预览和锁内状态绑定、质检/物流签名意图及已确认退货纠错仍未完成。

## Core 退货确认预览与绑定执行

新增两类 `agent-approval-previews/returns` 与 `agent-approvals/returns` 服务入口，复用现有审批策略、票据与完整确认命令结构。预览包含来源、退货版本、日期/原因、逐行库存与隔离影响、退货成本、原始往来与未结余额变化。原始单据字段与完整 guard 一起进入 previewHash；普通浏览器确认仍保留原输入和幂等摘要。

执行在来源/订单、往来及库存锁取得后重查来源与订单版本、往来版本、库存数量/价值/预留/隔离/最后流水和移动平均成本；变化则拒绝，需要重新预览和确认。预览也取得相关锁读取一致的状态，结束后回滚只读事务，不改变业务记录。Core 将上游已验证的确认信息绑定到预览，不代表 Gateway/Host 的实际签名链路已完成。

采购退货清空某 SKU 库存时结转全部剩余库存价值，部分退货后重新计算余额平均成本，防止舍入造成流水成本与库存余额不一致。确认实现拆入独立文件，保持每文件大小限制。

迁移 0041 扩展两类审批单据约束、登记六项 read/create/approve 能力；不自动授予权限或创建策略。完整签名工具与质检/物流处置意图尚未接入，迁移及服务尚未部署。

隔离数据库 `return_confirmation_final3` 的 B2 全闭环通过，包含两类预览→确认→处置和逐行效果回读；旧摘要、夹带字段、撤权、重复确认被拒绝。审批持久化插入门闩在预览核对后暂停请求，期间增加库存预留，再放行执行；正确实现返回 409，负向控制跳过库存检查后错误执行并返回 200，测试失败，已恢复防护。实际期初→采购收货→销售出库→全量采购退货场景证明清空后数量、价值及流水成本均归零。最终相关测试与严格 Clippy 通过。

## Core 质检、发运与签收意图

新增 `sales_return_inspection_intent`、`purchase_return_dispatch_intent`、`purchase_return_acknowledgment_intent`。固定接口提供不持久化的影响预览、30 分钟不可变意图、重读预览及完整确认/拒绝命令。三类命令分别反序列化为既有严格 DTO，拒绝未知字段；外层 sourceDocumentId 与 command 也拒绝未知字段。

质检绑定所有退货行的接收/报废量、冻结成本、数量/价值/预留/隔离与最后流水，锁内重查后执行。发运绑定当前退货版本、日期、承运商和运单号；供应商签收绑定版本、日期和说明，两者只改变物流状态，不改变库存或往来。范围涵盖法人、业务单元、仓库、客户/供应商、冻结和当前品牌；预览返回带范围信息的行。确认仅从已存意图取参数。原浏览器输入和幂等摘要保留。

迁移 0042 新建意图表与不可变触发器，扩展审批/委托类型并登记六个 create/approve 能力，不自动授权或初始化策略。

隔离新库 `return_disposition_final` 全闭环通过：三类准备/确认、幂等准备、同键变参冲突、拒绝不执行、过期意图、未知字段/非法参数、仓库撤权、旧摘要、确认夹带参数、重复确认与数据库禁止修改意图。采购发运/签收还验证既有业务幂等重放。质检审批在预览核对后的真实数据库锁等待期间，新增并过账 0.25 件、成本 12.5 的测试期初库存；执行拒绝旧影响，重新准备后实际库存/成本与新预览一致。故意移除锁内库存检查后出现错误执行（200 而非 409），负向测试失败，恢复检查后全绿。Core 严格 Clippy、格式和文件大小门禁通过。
