# 库存盘点助手接入

## 当前业务行为

`InventoryCountService::create` 直接创建 counting 状态并保存库存快照。数据库触发器在 counting/counted 期间阻止该法人、仓库和 SKU 的库存流水与余额更新，因此它会影响实际履约，不能作为无副作用的普通草稿工具。submit 录入全部实盘行并转为 counted；post 写差异流水、库存余额、盘点事件及审计并释放冻结；cancel 释放未过账盘点的冻结。

完整接入需包含范围与逐行库存查询、准备/确认冻结盘点、实盘录入、差异预览/过账、取消解冻和对应详情链接。所有改变实际流程状态的操作使用服务端保存并绑定完整参数的意图和签名确认。数量、盘盈成本与日期必须来自用户；不自动把账面数视为实盘数。已过账纠错必须有明确补偿语义，不能删除原流水。

## 已完成的底层校验修复

- submit 拒绝重复 countLineId，避免 BTreeMap 将重复行静默覆盖。
- submit/post/cancel 的幂等回放必须匹配当前盘点 ID；相同键和相同请求体用于另一个目标时返回 IdempotencyConflict。保留原请求摘要格式，使原浏览器请求的正常重试兼容。
- 测试种子拆到独立文件，避免继续扩大原 B2 测试文件。

隔离 PostgreSQL 数据库 `inventory_count_integrity` 完整 B2 流程通过。新增三张零差异盘点验证重复行拒绝且版本/状态不变、三类跨目标幂等键拒绝、同目标 submit/post/cancel 重放成功、取消正常解冻和零差异不产生库存流水。日志 `/tmp/business-count-integrity.log`。Core all-targets 严格 Clippy、格式和文件大小门禁通过，日志 `/tmp/business-count-integrity-{clippy,size}.log`。这不是非零差异、并发冻结、助手工具或真实聊天的完成证据；本批尚未部署。

## 接入前仍需完成

1. 当前业务单元与商品品牌范围已补齐，见下方验证记录；尚需冻结创建时的业务单元与逐行品牌，定义历史记录与主数据变化后的双重范围语义，以及锁等待期间的再检查。不能把当前主数据权限检查视为历史范围冻结已经完成。
2. 读取每行当前数量、预留、隔离、价值、均价、最后流水和版本，冻结准备仅保存意图；确认锁内重读比较后创建盘点。避免“新增盘点”直接冻结库存而无影响确认。
3. 实盘录入必须绑定全部行、精确数量/成本和当前版本；补齐修改/重录的业务状态语义。差异过账预览与执行共用计算，证明非零盈亏、清零成本、保护数量、并发/失败回滚及冻结释放。
4. 取消绑定盘点版本、用户原因及释放范围；已过账纠错另行设计并保留原始记录。
5. Gateway、Read API、固定 MCP 工具、Host 签名指令、权限迁移、详情页面与资源链接；Host 普通能力数量当前 46，后续扩展需解决现有 48 项上限，不能静默遗漏已有能力。
6. 配套部署、运行时工具集验证和获得具体授权后的实际聊天验收。

其他完整流程域仍按 [覆盖清单](full-workflow-coverage.md) 推进，盘点基础修复不代表整体目标完成。

## 当前盘点数据范围修复

盘点 options 在 LIMIT 前过滤仓库业务单元和 SKU 当前品牌；list 在 LIMIT 前检查仓库业务单元，并要求整张盘点的所有商品品牌都可访问，不通过隐藏部分行来暴露一张不完整单据。detail、submit、post、cancel 共用单据范围检查；create 在进入幂等处理前检查所选 SKU 和仓库的当前品牌、业务单元范围。现有法人、仓库及能力检查保留，未设置品牌的商品沿用既有领域规则。

新隔离数据库 `inventory_count_scopes` 的完整 B2 流程通过。测试分别撤销业务单元、品牌、仓库、法人：可选库存/列表为空，详情拒绝；创建、录入、过账和取消的新请求及已成功请求的幂等回放均返回 NotFoundOrForbidden；恢复范围后读取原单状态不变。Core all-targets 严格 Clippy、格式和文件大小门禁通过。日志 `/tmp/business-count-scopes{,-clippy,-size}.log`。测试源码使用固定 SQL 字面量，不绕过 SQLx 的动态 SQL 检查。

本批未部署、未接入助手工具。当前范围检查不冻结原始主数据，也不证明所有并发撤权/主数据变化窗口已覆盖；需随盘点冻结意图与锁内比较继续完善。
