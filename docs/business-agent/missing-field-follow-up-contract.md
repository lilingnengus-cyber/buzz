# BizOS 缺失业务字段补问契约

本契约统一 BizOS 在创建草稿、修改草稿、确认已发生收付款、核销、逆转和其他需要完整业务选择的场景中的补问。目标是让用户每轮都能看到已经保留的信息和一次性完整的缺失清单，避免重复追问或丢失已确认内容。

## 回复结构

字段不完整时，回复按以下顺序组织：

1. “已确认：”列出受验证的当前对话中用户明确提供或确认的业务值。
2. “还缺：”一次性列出完成本次操作所需的全部缺失字段。
3. 给出一个与当前操作对应的明确补充格式或受控录入链接。

不要重复追问已确认且未被更新的字段。不要把工具解析出的内部 UUID、历史订单中的值、默认配置或名称相似结果写进“已确认”。内部 UUID 只能在工具调用内部使用，不要求用户提供。

## 按操作列出字段

只列本次操作相关的字段，避免泛化清单：

| 操作 | 常见已确认／还缺字段 |
| --- | --- |
| 销售／采购／出库／收货草稿 | 客户／供应商、商品／SKU、数量、单价、币种、业务日期、仓库、计量单位、各行项目和必要归属 |
| 客户收款／供应商付款记录 | 往来方、金额、币种、业务日期、付款方式、外部参考号 |
| 草稿修改 | 明确目标、当前版本、保留或替换的行项目及用户要求修改的字段 |
| 应收／应付核销 | 收付款来源、应收／应付目标、当前版本、各笔金额 |
| 逆转、暂停、取消、盘点、退货和其他确认准备 | 明确目标、当前版本、原因、实际发生日期及该操作特有的逐行数量／成本／物流或质检信息 |

名称对象尚未唯一解析时，客户／供应商、商品／SKU、仓库或计量单位仍属于“还缺”。只有用户明确选择且工具验证后的对象才进入“已确认”。

## 更新与冲突

- 用户后续明确更新同一字段时，以最新明确值为准。
- 最新值与已确认值、已解析对象、其他字段、当前版本、授权范围或业务校验冲突时，先说清冲突，再一次性补问全部受影响字段。
- 不静默覆盖、混用新旧值或只更新部分关联行。变更客户、商品／SKU、仓库、业务日期、币种、数量或单价时，应重新校验受影响的名称解析、范围、价格、库存、版本或行项目。
- 当前对话没有可验证的已确认值时，不把聊天历史猜作确认；请用户重新提供该字段。

## 写入边界

字段仍缺、名称候选仍歧义、结果为部分结果、分页未完成，或关联校验未完成时，不调用写入工具，也不生成确认预览。收到补充后保留未受影响的已确认字段，只重验受影响项目；全部业务选择已明确且当前验证通过后，才可继续创建草稿、修改草稿或准备确认。

受控录入链接可以帮助用户补全字段，但链接不携带业务数据、凭据、查询参数或片段，且不表示已经保存任何草稿。

## 示例

> 已确认：客户 CUS_DEFAULT（默认客户）；商品 SKU_DEFAULT（默认商品 SKU）。
>
> 还缺：数量、单价、币种、业务日期、仓库和计量单位。
>
> 请一次性补充，例如“2 件，每件 CNY 100，2026-09-25，杭州仓，件”。
>
> [填写销售订单](biz://sales-order-entry)

如果用户随后将单价改为 `CNY 120`，仅更新单价并重验相关金额与行项目；客户、商品／SKU、数量、日期、仓库和计量单位仍保留为已确认值，除非用户同时更新它们。
